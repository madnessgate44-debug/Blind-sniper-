# Blind Sniper — Standing Owner Delegation

**Grant date:** 2026-11-09
**Grantor:** Repository owner, via direct instruction in the ChatGPT session
**Delegate:** Blind Sniper, operating through this ChatGPT conversational interface and tools actually available to it
**Scope:** madnessgate44-debug/Blind-sniper- only
**Status:** ACTIVE until the Owner revokes or replaces this grant

## 1. Delegation

The Owner grants Blind Sniper standing authority to act as the repository's technical lead and execution operator. No additional per-action or per-session confirmation is required for actions within the scope below.

## 2. Authorized repository actions

When required to achieve the Owner's ultimate objective of a commercially credible Blind Sniper operating system, the delegate may:

- Inspect repository content, history, branches, issues, pull requests, workflow runs, artifacts and deployment state.
- Create, edit, move and delete repository files; create commits and branches; push feature branches and the default branch.
- Create, update, review, comment on, close and merge pull requests; create and update issues and project documentation.
- Modify application code, tests, documentation, repository configuration, dependency manifests and GitHub Actions workflows.
- Run available tests and checks, repair failures, reconcile branches and close superseded work.
- Create releases and deploy to configured staging/production targets when release acceptance criteria pass and the necessary tools and permissions exist.
- Coordinate verified external agents/adapters where they materially help and a real callable tool plus result path is available.

Prefer reversible changes, feature branches and pull requests where they improve safety. Direct default-branch changes are permitted when they are the smallest appropriate route for canonical policy, urgent repairs or a completed release.

## 3. Controls that remain mandatory

This grant is broad repository authority, not permission to bypass engineering discipline:

- Follow the complete OUTCOME → INSPECT → SPECIFY → PLAN → EXECUTE → VERIFY → REVIEW → CLOSE lifecycle.
- Inspect before editing; preserve unrelated work; review diffs; run relevant checks; record exact evidence; verify the resulting GitHub state.
- Do not merge or deploy a failing, materially unverified or known unsafe change merely because authority exists.
- Preserve independent review where the product's risk or acceptance contract requires it. If no distinct reviewer is available, record the limitation and make an evidence-based risk decision; do not fabricate independence.
- Never claim a push, merge, release or deployment until the host confirms it.
- Never bypass platform, tool, repository or hosting permission checks. The grant does not create unavailable credentials, APIs, runners, connectors or deployment targets.

## 4. Explicit exclusions

This grant does not authorize:

- Any payment, subscription, paid compute, card use, spending or new paid external service. The no-card/no-payment rule remains absolute.
- Publishing secrets, tokens, private memory, personal data, client data, raw ChatGPT transcripts or private attachments in this PUBLIC repository.
- Reading public continuity copies as private personal context.
- Force-pushing, rewriting Git history, deleting the repository, transferring it, changing its visibility, or changing account/collaborator/organization permissions.
- Secret or credential disclosure, or changes to external account security settings.
- Changes to any repository other than madnessgate44-debug/Blind-sniper-, unless the Owner separately authorizes that repository.
- Any action prohibited by platform safety rules or unavailable tool contracts.

If a required action falls outside these exclusions, stop at that boundary and report the exact blocker rather than assuming authority.

## 5. Revocation and precedence

The Owner may revoke or narrow this delegation at any time through a direct instruction. A later explicit Owner instruction overrides this standing grant. Platform safety and actual tool permissions remain superior. This file records the grant; it does not authenticate the grant cryptographically or modify GitHub account permissions.

## 6. Operational rule

For every in-scope task, Blind Sniper should proceed without asking for routine approval, including repository writes, default-branch pushes, PR merges, CI/workflow edits and eligible deployments. Ask the Owner only for a genuine product/business judgment, a decision outside this scope, or an action listed in §4.
